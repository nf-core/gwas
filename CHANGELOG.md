# nf-core/gwas: Changelog

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/)
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## Development

### Added

- Added production LDAK 6.3 SumHer and SumCors routes with request-owned tagging references, canonical-summary adaptation, complete native result retention, normalized estimand and diagnostic views, liability-scale routing for complete prevalence declarations, and structural native-argument firewalls.
- Added the `NORMALISE_PHENOTYPES` local module, which normalises each analysis unit's phenotype and covariates once into a canonical layout: the trait at a fixed third column named `PHENO`, binary traits coded `0`/`1`/`NA` (the only coding PLINK 2, REGENIE, GCTA and LDAK all accept), missing values always the literal `NA`, quantitative and categorical covariates kept in separate files, and every file emitted in both a headered and a headerless serialisation because REGENIE requires a header and GCTA forbids one. The fixed column position makes GCTA's and LDAK's `--mpheno` a constant `1`. A `--save_normalised_phenotypes` save control, default `false`, publishes the headered files under `phenotypes/<analysis_id>/`.
- Added the `PLINK2_GLM` local module and wired PLINK 2 `--glm` as the pipeline's first end-to-end association route, with Firth fallback on binary traits and allele frequency and sample count columns requested explicitly for the harmonisation that follows. Results are published unmodified under `association/plink2/<analysis_id>/` as `<analysis_id>.plink2.glm.*`.
- Added the `GWASLAB_HARMONIZE` local module and passed every association result through it, so results from different methods on the same analysis are directly comparable — one canonical column set, allele orientation and variant identifier regardless of which programme produced them. Native association output is preserved unmodified alongside it. Every harmonised result now receives the stable identity `<analysis_id>--<association_method>` and is published once under `summary_statistics/<summary_statistics_id>/` as a canonical table plus provenance sidecar. Explicit column mappings are registered for all four association methods — PLINK 2, REGENIE, GCTA fastGWA and LDAK-KVIK — in one table, and the accepted `association_methods` vocabulary is derived from that table, so a route is selectable exactly when its mapping exists and adding a further route needs no new harmonisation component. Effect sizes and standard errors are written in scientific notation, because GWASLab's default fixed four-decimal format destroys them at the magnitudes a well-powered study produces.
- Added first-class summary-statistics and reference declarations. Runs may now ingest explicit-format raw external summaries through GWASLab, validate already-canonical external summaries without reharmonising them, or bind pipeline-generated association results through deterministic producer identities. Summary entities own unary SumHer/LDSC H2 selection; relationships resolve analysis and summary endpoint domains; method options expand deterministic primary and independently configured named unary/pair requests; and request-selected LDAK/LDSC bundles stage typed resource roles from a global reference catalog. All origins converge on `nfcore_gwas_canonical_v1` and publish safe checksum and transformation provenance without republishing source/intermediate duplicates.
- Added standalone CBIIT Python 3 LDSC H2 and ordered RG production routes. Content-identical canonical summaries reuse one HapMap3 munging result; request-owned LD-score and regression-weight directories enter only at estimation; observed and eligible liability invocations remain native request artifacts; mixed-trait marginals and covariance receive endpoint-aware scale attribution; and normalized heritability, covariance, correlation, diagnostics and provenance views retain every requested result without ranking methods or publishing munged intermediates.
- Added REGENIE as a complete association route using the reusable `plink_fit_regenie` and `plink_association_regenie` compositions. Standard Step 1 is the default and native split-L0/run-L0/run-L1 execution is available for larger cohorts; both feed Step 2 and the existing explicit GWASLab mapping. Scientific Step 1 block-size and binary Step 2 controls live in the per-analysis `regenie` method-options family, while execution mode, task sizing and low-memory behavior remain run/profile configuration. `--save_association_predictions` publishes analysis-attributed Step 1 bundles for both REGENIE and LDAK-KVIK.
- Added LDAK-KVIK as a complete association route using the reusable `plink_association_ldak_kvik` composition and the shared lazy PLINK 1 derivative. The required row policy selects all predictors, LDAK's thinned common set, or a supplied extract list for Step 1; Step 2 native output is published under `association/ldak_kvik/<analysis_id>/` and passed through the registered quantitative or binary GWASLab mapping. A dedicated `test_ldak` profile and fixture-backed tests exercise all three subset policies and both trait mappings.
- Added six optional GWASLab reference parameters — `--gwaslab_reference_fasta_grch37`/`_grch38`, `--gwaslab_rsid_vcf_grch37`/`_grch38` and `--gwaslab_strand_vcf_grch37`/`_grch38` — selected by the genome build declared by each cohort and by nothing else, with index sidecars resolved by convention. A build with no configured resource is still standardised, without one.
- Added the `PREPARE_RELATEDNESS_MATRICES` local subworkflow, which builds each distinct relatedness matrix exactly once and fans it back out to every analysis that needs one, so several traits sharing a cohort and a kinship model cost one matrix build rather than one each. Matrices are addressed by a reuse key: a SHA-256 digest, truncated to twelve characters, over the cohort, the genotype format, the sorted genotype file names, the matrix kind and the matrix's declared construction settings — and over nothing else, so per-trait sample missingness and trait identity cannot fragment it. The key is content-derived rather than arrival-ordered, so adding an analysis-manifest row does not renumber the matrices already built and invalidate `-resume`. Declared values are canonicalised before hashing (numbers and strings spelling a number both render through `BigDecimal` with trailing zeros stripped), so a value parsed from a manifest cell and the equivalent value filled in from a schema default never produce two keys for one matrix, while identifiers are rendered verbatim so two cohort names are the same only when they are spelled the same. GCTA's partition count is deliberately outside the key — the merged matrix is byte-identical whatever the count, so it is a memory control rather than a construction setting — and two rows sharing a key while declaring different counts are refused before any task starts, with an error naming the analysis units, the key and the values.
- Added `--save_relatedness_matrices`, default `false`, which publishes each merged relatedness matrix under `quality_control/relatedness_matrices/<key>/`, addressed by reuse key rather than by cohort because one cohort can carry several distinct matrices and a shared matrix belongs to no single analysis. Per-partition files and tool logs are never published.
- Added GCTA GREML as the pipeline's first heritability route, selected by the `gcta_greml` token in `heritability_methods` and built on the shared relatedness matrix mechanism above. Native GREML output is published unmodified under `heritability/individual/gcta_greml/<analysis_id>/` as `<analysis_id>.gcta_greml.hsq`; a binary trait declaring a `population_prevalence` additionally reports the estimate on the liability scale. Heritability estimates are not harmonised, unlike association results. This wires the vendored `gcta/makegrmpart` and `gcta/reml` modules, which until now were exercised by nothing, and vendors `custom/gctamergegrmparts` plus the `plink_prepare_grm_gcta` and `grm_heritability_gcta` subworkflows from the shared component library.
- Added LDAK REML heritability, selected by `ldak_reml`, using the shared relatedness-matrix reuse mechanism and the vendored `plink_prepare_grm_ldak` and `grm_heritability_ldak` subworkflows. LDAK kinship keys include the declared model, power and weights identity: equal weighting records its mode, while a supplied weights file records a SHA-256 digest of its bytes rather than its path or basename. The per-analysis relatedness filter is excluded, so filtered and unfiltered analyses share one `LDAK_CALCKINS` build. Native `.reml` output publishes under `heritability/individual/ldak_reml/<analysis_id>/`, with an additional `.reml.liab` file for binary rows declaring population prevalence.
- Added GCTA fastGWA-MLM association for quantitative and binary traits, selected by `gcta_fastgwa`. Each analysis reuses a compatible sparse relatedness matrix, publishes the native result under `association/gcta_fastgwa/<analysis_id>/`, and contributes a registered GWASLab-standardised summary-statistics table.
- Added GCTA GREML-LDMS heritability, selected by `gcta_greml_ldms`. The route partitions variants by configurable LD-score and MAF strata, reuses each compatible stratified matrix family, and publishes the native `.hsq` result under `heritability/individual/gcta_greml_ldms/<analysis_id>/`.
- Added LDAK Haseman-Elston and PCGC heritability routes, selected by `ldak_he` and `ldak_pcgc`. Both reuse compatible LDAK kinship matrices; covariate-aware analyses align phenotype residualisation with matrix adjustment, and PCGC requires population prevalence for its binary-trait estimate.
- Added route-aware MultiQC reporting. The report records the validated analysis plan, joined cohort and trait provenance, requested association and heritability methods, workflow parameters, method descriptions and software versions without representing requested routes as completed results.
- Added MPH heritability and bivariate REML routes, selected by the `mph_reml` and `mph_reml_ldms` heritability tokens and by `mph_bivariate_reml` and `mph_bivariate_reml_ldms` in a relationship manifest's `relationship_methods`. MPH fits a REML variance-component model by MINQUE with a stochastic trace estimator, over one component spanning the autosomal variant universe or one component per LD-by-MAF stratum of the shared component plan. MPH builds its own relationship matrices, whose layout is not interchangeable with GCTA's, so the `mph/makegrm` module constructs them natively from the same named SNP groups every other stratified family uses. The reusable `fit_mph_reml` composition pairs the `mph/reml` module with the pipeline-owned `prepare_mph_inputs` helper, which re-encodes the prepared phenotype and covariate tables into the IID-keyed CSV layout MPH's own documentation requires; a caller holding native-ready CSVs invokes `MPH_REML` directly. Heritability fits publish their native `.mq.vc.csv`, `.mq.blue.csv`, `.mq.iter.csv`, `.mq.cor.csv` and log under `heritability/individual/<method>/<analysis_id>/`, and pair fits under `requests/<method>/<request_id>/`. The per-individual `*.mq.py.csv` projection is deliberately not published: it scales with the cohort and is individual-level data.
- Added the `COMMON_VARIANT_META_ANALYSIS` composition, which runs the explicitly selected common-variant meta-analysis models on one genome-wide request over GWASLab-standardised member summaries. `GWASLAB_METAANALYZE` always emits a fixed-effect table and optionally a conventional random-effect table, and its aligned adapter products feed a thin `METASOFT_RE2` invocation that emits RE2's native result and log. `CUSTOM_PREPAREMRMEGAINPUT` adapts all parents once in declared study order with an explicit quantitative or binary trait type, and `MRMEGA` then runs once genome-wide, emitting MR-MEGA's native `.result` and `.log`. The composition carries no common result normaliser, no cross-programme assembler, no derivation sidecar and no chromosome scatter/gather; each model publishes separately under `requests/<model>/<request_id>/`.
- Added the reusable `sumstats_heritability_ldsc` and `sumstats_geneticcorrelation_ldsc` compositions, which munge each declared summary producer exactly once with the `ldsc/mungesumstats` module and then fit every request that references it — unary heritability through `LDSC_H2`, ordered pairs through `LDSC_RG`. Munging optionally takes a merge-alleles reference list, so an analysis restricted to a reference variant subset such as HapMap3 declares that list as a resource rather than pre-filtering its summaries, and a producer consumed by a unary request and by either side of any number of pair requests is still munged once.
- Added the relatedness-matrix builders as reusable compositions of their own. `plink_prepare_grm_gcta` constructs and merges one dense GCTA matrix from its row partitions; `plink_prepare_grm_groups_gcta` builds an ordered GCTA matrix family from caller-defined SNP groups, leaving row partitioning and ordered merging inside the single-matrix builder; `plink_prepare_ldms_plan_gcta` builds one LD-by-MAF component plan — a genotype view's LD scores and the ordered, disjoint SNP groups derived from them — as an artifact in its own right, because it is the shared input of every LD- and MAF-stratified family rather than a private step of any one tool's builder; and `plink_prepare_grm_groups_mph` builds the matching native MPH family from the same named groups through `CUSTOM_MPHSNPINFO` and `MPH_MAKEGRM`, emitting the per-family SNP counts beside it.
- Added a usage note on [mounted VCZ cohorts](docs/usage.md#mounted-vcz-cohorts): a VCF Zarr store can be served to the pipeline as an ordinary PLINK 1 trio by BioFuse, and the recommended way to do so is the planned `nf-biofuse` Nextflow plugin. The pipeline treats the mounted files as ordinary PLINK 1 input and needs no BioFuse-specific code.
- Added the `single_node` profile, which runs every task with the local executor inside one compute allocation instead of submitting each to the scheduler, for inputs visible only on the launching node such as a mounted VCZ cohort. It caps task and executor resources at the allocation, read from `SLURM_CPUS_ON_NODE` and `SLURM_MEM_PER_NODE`, falling back to every host core and 8 GB outside one or under `--mem=0`, and selects no container engine: use `-profile single_node,apptainer` or `-profile single_node,singularity`.
- [#95](https://github.com/nf-core/gwas/pull/95) - Add the `regenie/runl1` module, completing the REGENIE Step 1 module set (`runl0`, `splitl0`, `runl1`, `step1`, `step2`).
- [#93](https://github.com/nf-core/gwas/pull/93) - Added LDAK local modules (addgrms, adjustgrm, calcgenotypeerrort2, calcinflation, calckins, createthinweights, filterrelatedness, he, kvikstep1, kvikstep2, pcgc, reml, thinpredictors) under `modules/local/ldak/`.

### Changed

- PLINK 2 `--glm` now requests `cols=+a1freq,+beta`, so the binary route reports `BETA`/`SE` instead of `OR`/`LOG(OR)_SE` and one GWASLab column mapping serves both trait types — otherwise the harmonised binary file would carry an odds ratio where every other method carries a log-odds beta. Native output is still published exactly as PLINK 2 wrote it; only the columns PLINK 2 is asked for changed, and the quantitative route is unaffected.
- Replaced the monolithic `conf/modules.config` with one configuration file per method family under `conf/modules/`, included by name from `nextflow.config`, so an additional method family adds a file rather than editing a shared one. The process-wide default publish directive — which publishes nothing — now lives in `nextflow.config` itself, and `.nf-core.yml` records the corresponding lint exemptions.
- Replaced the legacy `--input` samplesheet with linked `--cohort_manifest` and `--analysis_manifest` inputs plus optional per-analysis `--method_options`. All association and heritability routes now share the relational contract. Cohort-owned genotype preparation is deduplicated and accepts PLINK 2 or PLINK 1 input, deriving PLINK 1 from PLINK 2 through the new `makebed` conversion module; VCF input is no longer accepted, so convert a VCF cohort to PLINK 2 or PLINK 1 before the run; matrix and prediction reuse identities include their scientific inputs; and portable relational examples and test profiles replace the retired monolithic fixtures.
- Moved pipeline-local route coverage into registered pipeline and subworkflow nf-tests, replacing duplicated module-local tests for vendored LDAK and GCTA components while retaining component tests for installed nf-core modules.
- Updated pull-request CI and test selection for the route-based layout, including broader nf-test triggers, reusable action inputs, the renamed lint-comment workflow and the current Apptainer setup action.
- Moved the five REGENIE modules — `runl0`, `splitl0`, `runl1`, `step1` and `step2` — from `modules/nf-core/regenie/` to `modules/local/regenie/`, so the pipeline owns the interface its `plink_fit_regenie` and `plink_association_regenie` compositions are written against rather than tracking an installed copy through `modules.json`. Their native command lines, outputs and container pins are unchanged; only their location and their installation record are.
- Both LDAK matrix builders now emit one collected kinship bundle instead of separate members. `LDAK_CALCKINS` and `LDAK_SUBGRM` each emit `tuple val(meta), path("<prefix>.grm.{bin,id,details,adjust}")`, so a base matrix and a subsetted matrix present the same shape to every consumer and `plink_prepare_grm_ldak` no longer re-maps the subset back into a bundle before emitting it. Consumers that need one member select it by extension. The files themselves are unchanged.
- Moved pipeline execution defaults out of `nextflow.config` into `conf/execution.config`, and merged the matching parameters into one `Execution options` schema group. The split it records is the placement rule: scientific specification — what is estimated and under which model — belongs in the analysis manifest's `method_options`; execution strategy — partitioning, execution modes, job counts, block sizes and low-memory behaviour — belongs in `conf/execution.config`; task `cpus`, `memory` and `time` belong in `conf/base.config`; and translation into native command lines belongs in `conf/modules/*.config`. `gcta_grm_parts`, `regenie_step1_mode`, `regenie_step1_jobs`, `regenie_lowmem` and `regenie_step2_bsize` now live together in that group, which additionally requires `regenie_step1_jobs` when `regenie_step1_mode` is `chunked` and forbids it otherwise.

### Fixed

- Removed the retired, unwired PLINK 1 association and VCF-conversion components, and repaired the `GCTA_ADDGRMS` and `GCTA_BIVARIATEREMLLDMS` test setups to use the pipeline-local `GCTA_MAKEGRMPART` process and their installed GAWK dependency.
- Corrected the lint workflow branch condition so it excludes automated nf-core template and module-update branches as intended.
- [#96](https://github.com/nf-core/gwas/pull/96) - Bump the `nft-utils` nf-test plugin to `0.0.9` for nf-test 0.9.4 compatibility (fixes `sanitizeOutput()` `MissingMethodException` in module tests after the 4.0.2 template merge).

### Dependencies

- Declared `conda-forge::r-base=4.3.1` in the `environment.yml` of the six LDAK modules that pin the `ldak6_r-base` image (`adjustgrm`, `fasthe`, `fastpcgc`, `he`, `pcgc` and `reml`). The pinned `ldak6_r-base` image and the new component conda locks both already carry that interpreter; only the package manifest was silent about it. A `-profile conda` run of those modules now installs the same set the container profile has always provided.
- Synced the vendored `modules/local/ldak/` family to the shared component library: the twelve name-matched modules now match the library byte-for-byte, `ldak/filter`, `ldak/subgrm` and `ldak/thincommon` were added, and `ldak/filterrelatedness` was removed in favour of the library's `filter` + `subgrm` split.
- Added MPH `0.55.1` as a newly wired programme, used by the `mph/makegrm` and `mph/reml` modules. MPH is not packaged for Bioconda, so both modules pin a container image by digest and carry no `environment.yml`; that image is `linux/amd64` only and statically linked against Intel oneMKL, so there is no Conda fallback and no other architecture.
- Added METASOFT `2.0.1` as a newly wired programme, used by the `metasoft/re2` module. METASOFT is distributed as a Java archive rather than a Conda package, so the module likewise pins its image by digest and carries no `environment.yml`, and sizes the JVM heap from the task's memory allocation.
- Added MR-MEGA `0.2` as a newly wired programme, used by the `mrmega` module. The release carries no identifier beyond the `0.2` its own `--version` banner reports, so the module pins the image published by MR-MEGA's authors by digest.
- Added LDSC `3.0.2` as a newly wired programme, used by the `ldsc/mungesumstats`, `ldsc/h2` and `ldsc/rg` modules. This is the Python 3 CBIIT fork at commit `6c673952cee74bd5c57aef1555a03b1c015399a0`, installed from its checksum-pinned source archive by `pip` in each module's `environment.yml` on top of `conda-forge::python=3.9.13` and the numeric stack LDSC requires; the container profiles pin the matching image by digest.
